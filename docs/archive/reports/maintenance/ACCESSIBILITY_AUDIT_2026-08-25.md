# تدقيق إمكانية الوصول لواجهة Telegram Drive Glow

**تاريخ التدقيق:** 25 أغسطس 2026
**النطاق:** واجهة Compose والمسارات Home وUpload preparation وQueue وHistory وSettings وTelegram Auth وTelegram Destination وOnboarding وSplash والتنقل التكيفي والمكونات المشتركة.
**حد التدقيق:** استخدمت WCAG 2.2 مرجعًا تقنيًا محايدًا لتدقيق Android Compose؛ لا يمثل ذلك شهادة توافق ويب أو شهادة AAA للتطبيق.

## الملخص التنفيذي

كشف التدقيق عن مسألتين مؤثرتين في قابلية القراءة: كانت طبقة الزجاج المشتركة ترسم انعكاساتها بعد المحتوى، وكانت بعض النصوص الوظيفية تعتمد على شفافية منخفضة داخل حاويات Glow. أُصلحت المسألتان. كما رُفع ضمان أزواج ألوان الإجراء المخصص والمحدد مسبقًا إلى هدف هندسي **7:1** للنصوص في `primary/onPrimary` و`primaryContainer/onPrimaryContainer`، مع جعل الحاويات الأولية معتمة قبل القياس. لا تتغير دلالات النجاح أو التحذير أو الخطأ، ولا يتغير TDLib أو المصادقة أو وجهة Telegram أو WorkManager أو الرفع الحقيقي.

النتيجة هي **تحسن برمجي موثق، لا جاهزية لإعلان توافق AA أو AAA كامل**. لا يتوفر هاتف أو محاكي أو `adb` في هذه البيئة، ولذلك لا يمكن إثبات ترتيب TalkBack، النطق، حجب التركيز، أبعاد اللمس الفعلية، الخط الكبير، RTL، أو استمرار التفضيلات بعد إنهاء العملية على جهاز.

## مصفوفة النتائج

| المجال | النتيجة | الدليل أو الإجراء |
|---|---|---|
| بدائل النص للأيقونات | مراجعة ثابتة مقبولة | الأيقونات التفاعلية المراجعة تحمل وصفًا؛ الأيقونات المجاورة لعناوين أو نصوص مكافئة زُوّدت بـ `contentDescription = null` بوصفها زخرفية. |
| اختيار الألوان | محسّن برمجيًا | صفوف الألوان والوجهات تستخدم `selectable` مع `Role.RadioButton`؛ العجلة لها سلايدرات Hue/Saturation/Brightness بديلة ودلالات حالة. |
| السحب | محسّن برمجيًا | اختيار لون العجلة ليس مسارًا وحيدًا؛ السلايدرات تعمل كبديل لا يحتاج السحب. |
| تباين النص الوظيفي | محسّن ومختبر | أزيلت شفافية نصوص المساعد والملخص والوجهة والاتصال. اختبارات Glow تفحص 7:1 للألوان المحددة وخمس حالات مخصصة في السمتين. |
| تباين الزجاج | إصلاح أساسي | انعكاس الزجاج والتوهج يرسمان الآن قبل المحتوى؛ النص وحلقة التركيز يقعان فوق الزخرفة. |
| تركيز لوحة المفاتيح | محسّن جزئيًا | حلقة `glowFocusIndicator` موجودة في محرر اللون وتملك اختبار 3:1؛ لا يوجد إثبات لتتابع التركيز أو عدم حجبه على الجهاز في كل المسارات. |
| الحركة | محسّن برمجيًا | حركة Aurora ومؤشر الرفع مربوطة بتقليل الحركة؛ Splash لا ينشئ انتقالًا لانهائيًا عندما تكون مدة رسوم النظام صفرًا. |
| RTL وتكافؤ الموارد | تحقق ثابت مقبول | فحص أسماء موارد `values` و`values-ar` متطابق. لا يوجد اختبار تخطيط RTL حي. |
| الاستمرارية | جاهز لاختبار جهاز | اختبار DataStore instrumentation يعيد إنشاء قارئ إعدادات، لكنه لم يُشغّل دون جهاز أو محاكي. |

## التحقق الآلي الإضافي

جُمِّع `:app:compileDebugAndroidTestKotlin` بنجاح؛ لذلك أصبح اختبار `SettingsDataStorePersistenceTest` صالحًا للتشغيل عند توصيل هاتف أو محاكي. كما فُحصت عناصر الاختيار المبنية مباشرة على Foundation. أضيف `heightIn(min = 48.dp)` إلى صفوف اختيار الثيم وألوان Glow، وإلى الجزء القابل للاختيار في صف وجهة Telegram. بذلك لا يعتمد هدف اللمس على سواتش بعرض 20dp أو أيقونة داخلية بعرض 40dp.

أعيد تشغيل `:app:compileDebugKotlin :app:compileDebugAndroidTestKotlin :app:testDebugUnitTest` بنجاح بذاكرة Gradle منخفضة وعامل واحد. لا يمثل تجميع اختبار Android تشغيله: لا يزال عدم وجود هاتف أو محاكي و`adb` حاجزًا أمام إثبات الاستمرارية أو TalkBack أو القياس الفعلي لأهداف اللمس.

## الإصلاحات المنجزة

### طبقة الزجاج القابلة للقراءة

في `LiquidGlassSurface.kt` أصبحت `drawRect` و`drawCircle` تنفذان قبل `drawContent()`. سابقًا كان الانعكاس يرسم فوق النص؛ ولذلك كان يمكن لخلفية ضوئية متغيرة أن تخفض التباين المرئي. الإصلاح يحافظ على الانعكاس والهالة، لكنه يعامل المحتوى وحالة التركيز بوصفهما الطبقة الأمامية.

### النصوص الوظيفية داخل Glow

أزيلت قيم alpha من النصوص التي تصف حالة أو قرارًا داخل بطاقات الرفع والوجهة والاتصال. بقي التسلسل البصري عبر أدوار Typography والمسافات، لا عبر جعل المعلومات أقل قابلية للقراءة. النصوص المخصصة للضوابط المعطلة بقيت خارج ضمان 7:1 في هذا التدقيق وتحتاج قرار منتج منفصل إذا كانت ستصبح قابلة للتشغيل.

### ألوان الإجراءات المحسنة

`GlowColorCodec.ensureEnhancedTextContrast` يعالج الألوان المحددة والمخصصة عند تطبيقها على `ColorScheme`. يختار foreground المناسب، ويعدل الخلفية تدريجيًا تجاه الأسود أو الأبيض حتى يصل إلى 7:1، ويجعل الحاوية الأولية معتمة قبل القياس. يحافظ هذا على هوية اللون قدر الإمكان، لكنه قد يغيّر درجة لون الاختيار المتطرف قليلًا لحماية النص.

### تقليل الحركة

توقفت Splash عن إنشاء نبضة لانهائية حين تكون `ANIMATOR_DURATION_SCALE` مساوية للصفر. تظل مدة البداية المختصرة والسلوك الانتقالي كما كانا، لكن لا توجد حركة زخرفية نشطة في هذه الحالة.

## التحقق المنفذ

| فحص | النتيجة |
|---|---|
| `GlowColorPresetTest` مع الألوان المحددة والمخصصة | ناجح عند هدف 7:1 |
| `:app:compileDebugKotlin :app:testDebugUnitTest` | ناجح باستخدام عامل واحد وذاكرة محدودة |
| `:app:compileDebugAndroidTestKotlin` | ناجح؛ اختبار الاستمرارية جاهز للتشغيل على جهاز |
| تكافؤ أسماء الموارد العربية والإنجليزية | ناجح |
| `git diff --check` | ناجح |
| اختبار Android instrumentation / TalkBack / AVD | غير منفذ؛ لا جهاز أو محاكي أو `adb` |

تحذيرات SDK XML وإهمالات Android/Room/Kotlin وKapt Moshi قائمة مسبقًا ولم تُخفَ خلال التدقيق.

## ما يجب اختباره قبل APK أو Release

1. تشغيل TalkBack يدويًا عبر جميع الشاشات، خصوصًا صفوف الألوان، عجلة اللون، السلايدرات، زر الحفظ، أزرار الوجهة، التنقل السفلي والـNavigation Rail.
2. اختبار لوحة مفاتيح أو Switch Access لتتابع التركيز، ظهور حلقة التركيز، وعدم حجبها بواسطة البطاقات الزجاجية أو شريط التنقل.
3. قياس أهداف اللمس الفعلية، وبالأخص أزرار الأيقونات وعناصر الاختيار، مع معالجة أي هدف أصغر من المتطلبات المنتجة.
4. اختبار خط النظام الكبير، تكبير الشاشة، الوضعين الفاتح والداكن، RTL، وتعطيل رسوم النظام.
5. تشغيل `SettingsDataStorePersistenceTest` على جهاز، ثم إنهاء التطبيق وإعادة فتحه يدويًا للتحقق من استمرار اللون المختار.
6. اختبار المصادقة والوجهة والرفع الحقيقي والإشعارات النهائية على جهاز، مع التحقق من عدم تأثير إصلاحات الواجهة في السلاسل المحمية.

## قرار الإصدار

لا أوصي بإنشاء **GitHub Release أو APK موجه للمستخدمين** بوصفه إصدارًا متوافقًا مع إمكانية الوصول حتى تكتمل قائمة الجهاز أعلاه. يمكن التفكير في APK داخلي لاختبار الجهاز فقط إذا طلب المستخدم ذلك صراحة، مع وصفه بوضوح بأنه بناء تحقق وليس شهادة وصول.
